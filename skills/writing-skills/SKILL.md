# Writing Skills

Create or correct reusable instructions from actual needs and observed failures. User scope, safety, verification, and output rules take precedence over this skill.

## Before editing

Read the selected skill completely, resolve its canonical source, and inspect relevant callers/resources. Use existing session evidence or a concrete source conflict as the baseline for a correction. Do not reconstruct an audit, invent pressure scenarios, or run a tests-of-tests loop for a reversible instruction edit.

Keep the capability discoverable with a concise name and description. Describe when the skill applies without attracting unrelated tasks. Preserve supported frontmatter and platform-specific metadata. Link detailed references on demand; avoid exhaustive examples, duplicate policy, and extra scaffolding.

## Write the smallest useful correction

Match procedural rigidity to actual risk. Give ordinary implementation technical discretion; reserve exact commands, target identity checks, and approval gates for fragile or consequential operations. A skill must not turn routine verification words into user-ordered gates.

Preserve explicit user decisions and authorization boundaries. Prefer deleting contradictory ceremony over adding another overriding paragraph. Keep one coherent workflow; no forced tiny tasks, per-packet fresh agents, automatic review chains, or post-green adversarial passes.

Update canonical sources and applicable installed mirrors together, preserving unrelated edits. Do not copy provider-specific tools into another agent unchanged. For a migration, resolve equivalent native tools, relative resources, discovery metadata, and missing capabilities. Reuse compatible shared resources rather than creating duplicate implementations.

## Verify and finish

Use one proportionate pass over the delivered changes: available frontmatter validation, reference/discovery checks, and configured quality gates. New or changed executable helpers need one meaningful runnable check of their behavior. Pure wording changes need no generated test harness.

Run a bounded behavioral evaluation only when explicitly requested or when a material unresolved behavior cannot be checked from the actual artifact. Do not recursively evaluate the evaluator or expand into speculative counterexamples. Existing real session failures need not be reenacted.

After the chosen pass is green, stop testing and complete authorized delivery. Do not delete user work because a test-first ritual was skipped. Commit, publish, install privileged runtimes, or alter hooks only when the current task authorizes those actions. State unverified behavior honestly; source validation does not guarantee future model compliance.
