# Subagent-Driven Development

Keep one parent task responsible for the approved outcome. Delegate independent work when it saves time or context. User instructions and explicit gates govern this skill.

For approved reversible projectless config/skill/app changes, work directly or use one implementer plus one verifier. Skip worktrees, commits, plan/spec artifacts, tasks JSON, review packages, and renewed execution approval.

## Size and ownership

A worker owns a coherent deliverable, including related implementation and integration. Split for independent ownership, dependencies, safety boundaries, or demonstrated context limits. Do not split by arbitrary file counts, time slices, or individual test steps.

Apply DeepSeek-first routing before duplicate primary discovery; delegate settled source/documentation outcomes together. Use current platform routing and preserve explicit task choices and pinned batch/recovery models. Cheap literal packets require exact edits and acceptance with no open choices. Ordinary implementation may use a capable worker with an outcome contract and appropriate technical discretion.

Reuse an available specialist with followup_task or the platform equivalent. Start a fresh worker for a different context domain or a demonstrated stuck approach. Supply relevant component/task guidance and evidence without copying the parent's transcript or unrelated procedures. Respect the user's child-agent cap.

## Dispatch

Give each worker: authoritative sources, ownership, outcome, authorized paths/hosts/operations, credential mechanism without values, prohibitions, acceptance, verification owner and result shape. Private access alone never reserves execution for the primary. Follow shared secure-execution rules; assign verification once.

Independent readers can work concurrently. Writers may overlap only in time, never in owned files or dependent state; otherwise serialize or isolate their checkouts. Tests that mutate shared environments are writers. Native tracking reflects actual active work before dispatch. Preserve existing task IDs, dependencies, and persistence; do not build a second tracker.

If an established plan has user-gate metadata, retain its full description, exact verification, evidence axes, and ordering. Do not reinterpret routine acceptance criteria as user approval gates.

## Handle results

- DONE: inspect the actual diff and returned evidence, integrate the approved work, then continue remaining requirements.
- DONE_WITH_CONCERNS: fix in-scope correctness issues; record unrelated observations without expanding scope.
- NEEDS_CONTEXT: provide source/decisions or inspect them yourself; do not relay answerable questions to the user.
- BLOCKED: inspect the mechanism. Correct routine environment/invocation faults, supply context, or change the approach/model when justified. Finish independent work. Escalate only the essential action that lacks authority, access, a material user choice, or a safe path.

Do not force unchanged retries. Agent-created packet sizes, review counters, and wave boundaries are not approval gates. Explicit user retry limits and destructive/safety gates remain binding.

## Verification and continuity

Choose verification or a specifically requested review; do not stack mandatory spec review, quality review, final review, and re-review loops. No automatic adversarial pass after green. Concrete failures follow the user's focused diagnosis budget; unrelated findings never extend the task.

For user-facing behavior, assign a browser exercise of the real running app on an authorized deployed target, otherwise runnable local/staging; no pass without observations. Reuse green checks. Use a focused runnable check only for a consequential hidden invariant, explicit gate, unavailable browser/app, or non-UI work; name the gap and smallest substitute. Use verification-before-completion for one proportionate final pass. Consume current evidence for unchanged components; preserve exact requested live checks. Never manufacture a pass.

Keep goal, authorization, settled decisions, completed evidence, remaining work, and next action in existing progress. After compaction, read that record and continue in the same task. Never redispatch completed work, require a new task solely by compaction count, archive the calling task, or delete another task's artifacts.

Complete all authorized delivery steps. Commit, merge, deploy, or delete only within existing authority. No per-task commit requirement, review package, synthetic audit, or automatic workspace deletion. Existing helper scripts/templates remain available only when a user explicitly requests their fuller workflow; they cannot override current scope or verification rules.
